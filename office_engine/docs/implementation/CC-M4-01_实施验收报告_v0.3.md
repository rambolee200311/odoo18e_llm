## 1. 结论摘要

CC 冻结的适用验收项均已完成。完整 Registry 上 40 条明确意图的 Retriever Top-5 为 **40/40**；同一 Thread 对完整 Registry 做两遍分页，均返回 757 个唯一模型且每页顺序逐项一致。Agent 40 个唯一明确任务最终均通过 `describe` 选中目标；4/4 技术歧义、4/4 业务歧义、6/6 负向表达和六组各三 Thread 重复样本均符合标准。

第一轮 Agent 盲测有一条 P04 在 Provider 首次调用时超时，没有进入 Discovery，因此该次的选模结论是 `NOT REACHED`。原始超时保留；随后在独立 Thread 用相同自然语言输入和工具配置单独重跑并通过。最终是 **40/40 个唯一明确用例有成功的选模与 describe 证据**，不是把首轮 39/40 改写为通过。

项目负责人已批准 CC-M4-01 正式关闭。冻结的 UI HVR 不适用于本 CC；本轮没有执行 UI HVR。未运行 M2 全量回归，不对该范围作通过声明。

## 2. 旧失败根因与实现调整

### 2.1 候选漏召回

历史直接 Retriever 实现使用固定相似度门槛，导致低分但仍可能相关的模型从候选中被丢弃。旧 Provider 实验又将 GPT 重排候选截为 50 项：隐藏 Oracle 中有六条目标不在这个候选池内（T01、T02、V03、SP03、AM03、PR03），GPT 无法将池外模型排进结果。旧直接 Top-5 真实命中为 18/40，旧 GPT 隔离实验中目标候选覆盖为 34/40。

本轮移除固定相似度门槛，对实际完整 Registry 757 个模型计算语义相似度；按量化后的相似度桶和模型技术名形成稳定底序，再将真实 Registry 元数据交给 GPT-5.6 Luna 通用重排。候选 ID 依据技术模型名的稳定顺序生成，Provider 结果只接受格式正确、唯一且属于本轮候选的 ID。没有固定业务模型、测试目标、业务词映射或盲测答案。

### 2.2 分页不稳定

历史实现按页重复计算 Provider 相关性并重复请求 GPT，完整遍历出现过页间 `count` 变化、集合不一致、重复或漏项。该机制不能证明同一逻辑查询的后续页来自同一排序结果；温度或提示词设置也不能给出这种保证。

现在首个 Thread `discover` 请求对完整 Registry 生成排序，并将模型顺序及 query、Registry、Provider、model 摘要写入现有 `mail.message` 的隐藏内部记录。后续页和同 Thread 重复遍历通过这些摘要检查并复用同一顺序。快照不进入 Provider 消息历史、不经 Discuss/Bus 向用户显示，也不加入公开 Tool 响应。若后续页找不到完整匹配的快照，执行失败关闭并要求从 `offset=0` 重启，不临时生成另一份排序来拼接。

该方案未新增业务模型、公开工具、Schema 字段或业务数据写入；快照只保存通用 Registry 模型名及完整性摘要。当前实现按 Thread 保留不同查询/Registry 版本的内部排序记录，没有新增 TTL；Thread 的生命周期负责消息清理。该存储增长边界列为后续运维观察项，不影响本轮分页验收。

### 2.3 GPT 重排 Thread 历史隔离

重排调用使用空 `mail.message` recordset 作为 `messages`，只通过 `prepend_messages` 传入一条专用 system 指令和一条包含本次合成业务查询及 Registry 元数据的 user 消息。`_office_m4_tv_audit_thread_id` 和 `thread_ids` 仅用于本地受控审计关联，前者在进入 Provider SDK 前被消费；Thread ID 未作为重排上下文发送给模型。

真实 OpenAI SDK 边界审计核对了出站请求中 `payload.messages`：40/40 直接盲测请求、66 个 Agent Thread 中 69/69 内部 GPT 重排请求、P04 重试中的 1/1 重排请求均只有 `[system, user]` 两条消息；没有任何其他 Thread 消息，没有工具 Schema。user JSON 的键严格是 `business_request` 与 `candidates`，候选数均为 757，每项只有 `candidate_id`、`model`、`description`、`rec_name`。对应 Provider response 均已收到。审计日志中的 Thread ID 位于请求事件的本地关联字段，不在 OpenAI SDK 请求 payload 内。

Agent 正常 Provider 请求则单独核对了工具绑定：Thread 初始工具及 Provider 请求 Schema 都只有现有 `odoo_record_retriever` 与 `office`。审计记录在 SDK 请求提交边界生成，不含 API Key 或 Authorization Header；每个请求 ID 均能和响应或错误事件对账。

## 8. 风险与未覆盖范围

- 当前隐藏顺序记录保存在 Thread 的 `mail.message` 中，每个新的语义查询/Registry 版本可能增加一条内部记录；本 CC 未加 TTL 清理策略。它不包含业务记录，也不参与用户可见历史。
- Provider 测试覆盖的是合成查询与 Registry 模型元数据；Agent 测试守卫阻断业务记录读取和 Office 写操作。因此本轮结果只证明发现/描述、工具链和分页能力，不证明数据导出 E2E 或业务结果生成。
- 本轮跑了 `office_engine_m3` 全模块测试；未运行 M2 全量回归、UI HVR 或生产环境测试。不得把未跑范围表述为通过。
- 一个真实 Provider 超时已保留，并完成同条件单例重试；重试结果补足测试覆盖，但没有抹除首次失败。
