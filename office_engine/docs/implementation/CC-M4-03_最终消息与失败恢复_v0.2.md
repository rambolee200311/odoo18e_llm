## 3. 范围

### 3.1 范围内

1. 沿实际链路调查 Thread 866：Provider SDK response → Adapter / Odoo LLM 消息处理 → assistant `mail.message` 创建与事务提交 → Silent Retrieval 分类 → Bus/SSE → Discuss 历史读取 / UI。

3. 确保成功的纯 Retriever 内部 Tool Call / Execute 继续保持用户界面静默，同时保留内部消息、上下文、执行状态和诊断。
4. 确保最终成功答复、澄清、权限拒绝、查询 / handoff / Office 失败、Office 与 Retriever 混合消息、Candidate 及用户确认事件不会被误分类或整条隐藏。
5. 按操作副作用分类验证只读纠正、权限停止、明确失败后的状态检查以及写操作状态未知时的安全停止。
6. 运行受影响的自动化与组件集成回归；维护 IHR、ATR、必要的 RCA / Final Report。中间 CC 不做 UI HVR。

## 5. 行为契约

### 5.1 最终消息生命周期

1. Provider 返回的最终答复、澄清或失败说明必须在 Odoo Thread 形成可持久读取的 assistant 消息；相关消息及业务状态必须处于正确的 Odoo 事务边界。
2. Bus/SSE 的实际对外可见事件不得早于消息持久化成功。优先复用 Odoo 现有事务后通知机制；业务代码不得为此直接调用显式 `cr.commit()`。不得先广播后分类或持久化。
3. 提交成功后刷新及重新打开 Thread，最终消息仍可读取；事务回滚时不得对外发布该消息；通知失败不得使已提交消息丢失，后续仍应可读取。空答复或未持久化不得被呈现为成功完成。
4. 消息、请求、工具调用和状态间可用现有 ID 关联；缺失的 Provider request/response ID 标为不可得，不造 ID，不记录凭据。

### 5.2 Silent Retrieval 边界

| 消息类别 | 用户可见性 | 内部保留 |
|---|---|---|
| 成功的纯 Retriever assistant Tool Call 与 Execute | 按 M3 已验证路径不显示为冗余业务消息，且不提前经 Bus/SSE 暴露 | 保留 mail.message、原始参数/结果、Tool Call ID、LLM 上下文、执行状态与诊断 |
| Agent 成功纠正的中间 Retriever 错误 | 可保持静默，不要求将每个中间错误单独展示为业务消息；不得据此宣称任务成功 | 完整保留原始错误码、诊断 ID、工具参数/回执，并准确提供给 Agent 后续上下文 |
| 最终未恢复的 Retriever 错误、ACL / Record Rule 拒绝或需用户介入的失败 | 必须将失败准确告知 Agent，并形成可持久读取的 assistant 失败说明供用户查看；不得隐藏最终失败答复 | 保留原始错误码、诊断 ID 和执行回执 |
| Office 与 Retriever 混合调用 | 不因含 Retriever 而整条隐藏；Office 与必要文本保持现有交互 | 全部保留 |
| 最终业务答复、澄清、失败、Candidate/Accept/Reject/Finalize | 按现有 M2/M3 交互正常显示 | 全部保留 |

静默分类按消息在任务中的作用判定：只有成功的纯 Retriever 中间消息，以及后来已由 Agent 成功处理的中间错误消息，才可不作为独立业务消息显示；原始内部记录与回执仍保留。最终未恢复错误、权限拒绝、需用户介入的失败、混合工具消息、最终答复和用户确认不得被静默过滤。若中间错误已纠正，只有在后续工具回执及最终结果支持任务完成时才可报告成功。

### 5.3 恢复与重试边界

| 操作 / 状态 | 允许行为 | 禁止行为 |
|---|---|---|
| Registry discover/describe 只读错误 | 依据实际错误调整同一失败操作，或按新发现的信息继续下一项合法步骤。同一失败操作最多进行 2 次纠正重试 | 无限或机械重试；在相同错误且无新证据时继续尝试；把空候选说成模型绝不存在；猜测技术答案 |
| Retriever `INVALID_QUERY` / `FIELD_NOT_FOUND` | 只在保留全部用户业务条件且使用元数据 / 成功回执支持的修正后重查。同一失败查询最多进行 2 次纠正重试 | 静默删减或放宽谓词、把错误报成零、相同错误且无新证据时继续尝试、超限继续请求 |
| Retriever 合法零结果 | 报告成功零结果；只有新证据或用户澄清后才改变查询 | 将零结果当作错误自动重试或推断全局无记录 |
| ACL / Record Rule 拒绝 | 准确报告当前用户不可读并停止；必要时请有权限的用户处理 | `sudo()`、换身份、改走其他路径绕权 |
| Office 写操作明确失败 | 按 M2/M3 现有契约核对适用的操作回执、Candidate / Current、附件、版本和 SHA，再按可证实状态处理 | 只看异常文本就认定无副作用并盲目重复创建 / 覆盖 |
| 任一存在副作用的操作状态未知 | 使用现有操作标识、执行回执和相关业务状态核对结果。Office 文件操作按既有 Candidate / Current、附件、版本及 SHA 契约检查；仍无法确定时停止自动重试并向用户说明 | 盲目重复执行。不得把 Office 文件检查项强加到不涉及该生命周期的其他操作 |

重试预算按“同一失败操作”计算：原始调用之外最多 2 次纠正重试，不按 `discover → describe → search` 等正常的新规划步骤累计。成功分页后读取下一页、根据已返回元数据发起新的合法查询，也不属于前一失败操作的重试。若同一操作重复出现相同错误且没有新证据，应提前停止，不得机械耗尽次数；不得通过重新命名阶段重置预算。所有尝试逐次留证。不能证明原条件、当前权限和副作用安全时停止。不得创建新 Candidate 作为错误恢复捷径；既有 M2/M3 Accept / Finalize 门禁不变。

Agent 可以决定是否对只读错误采取有界纠正，但执行层权限和副作用保护不能只依赖 Prompt。优先验证现有执行层已提供的防重复或状态门禁；本 CC 不新增通用幂等框架。

| CC-TEST-009 M2/M3 定向回归 | 自动化回归 | 运行本次影响的消息、Silent Retrieval、M2 生命周期和 M3 测试 | 既有公共接口、审计留存、混合工具、错误可见、Candidate/Current 和用户确认无回归；未运行项不宣称通过 | 精确测试命令、用例名、日志和基线差异 |

真实 Provider 任务仅使用合成自然语言、合成 Thread/记录与隔离故障；Oracle 不进入 Agent 或 Provider 上下文。工具使用普通 Odoo 用户。任何测试专用观察 / 故障入口必须受测试开关和白名单约束，结束后撤销并通过 ORM 复核清理。

## 8. 关闭标准

CC-M4-03 仅在负责人关闭评审前满足以下条件：

- Thread 866 历史根因结论与当前隔离故障注入结论分开记录；历史证据不足时允许如实保留 UNKNOWN，不得以新测试替代历史因果证明。当前故障路径必须达到 CC-TEST-001 的持久化与可读取标准。
- 最终答复、澄清和失败消息在正确 Odoo 事务边界内持久化；Bus/SSE 只在持久化成功后对外可见，回滚和通知失败行为符合 CC-TEST-002，且业务代码不直接执行 `cr.commit()`。
- Silent Retrieval 保留全部内部记录；成功或已恢复的纯 Retriever 中间消息可静默；最终未恢复错误、权限拒绝、混合工具和确认链不被隐藏。
- CC-TEST-006 按同一失败操作核算有界纠正及每次 Agent 决策；CC-TEST-007 验证实际存在的执行层安全保护，不把 Prompt 当作唯一副作用防护。ACL 拒绝、合法零结果、写操作确定失败和状态未知逐类覆盖。
- M2/M3 受影响回归通过；Provider / Tool 公共接口保持兼容；测试注入设施撤销且数据清理有证据。
- IHR、ATR、FR 完整；每个强制测试均有状态和证据；失败项按项目流程处置；最终由负责人决定关闭。
