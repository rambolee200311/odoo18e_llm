## CC-TEST-006：真实 Provider 的 Retriever 错误恢复

采用真实 Odoo Thread、真实 Provider Tool Calling、当前用户 Retriever ORM 和独立 ORM Oracle。每个 Thread 只绑定只读 `odoo_record_retriever`。测试程序不向 Agent 提供模型、字段、Domain 或 Oracle 记录答案。注入发生在 Tool Execute 边界：`INVALID_QUERY` 分支在本次执行参数中附加 `search` 不支持的 `query`，`FIELD_NOT_FOUND` 分支附加本次随机生成的不存在字段；随后调用实际 Retriever，由它返回原生错误。注入请求未执行 ORM 业务记录搜索。

| 错误场景 | Thread | Provider 请求/响应 | 实际行为与 Oracle | 判定 |
|---|---:|---:|---|---|
| 单次 `INVALID_QUERY` 后纠正 | 2119 | 8 / 8 | Provider 收到原生 `INVALID_QUERY` 后重新发起兼容的 legacy search，解析公司，再查询联系人。最终查询保留直属父记录、启用状态和邮箱非空条件；完整结果为 Oracle 的两条目标联系人，排除了无邮箱、已归档及其他父记录。最终答复包含准确人数和两组原始姓名/邮箱。 | PASS |
| 单次 `FIELD_NOT_FOUND` 后纠正 | 2122 | 7 / 7 | Provider 收到原生 `FIELD_NOT_FOUND` 后使用此前 `describe` 返回的字段信息纠正检索；联系人查询保留直属关系、启用状态和邮箱条件，ORM 结果身份及最终姓名/邮箱与 Oracle 完全一致，反例均未输出。 | PASS |
| 重复 `INVALID_QUERY` 后停止 | 2123 | 6 / 6 | 相同错误经两次搜索调用返回（初始调用 + 1 次纠正重试）。没有成功的业务搜索结果；Agent 明确报告无法完成，不把错误当零结果、不编造人数或名单，也未超过最多 2 次纠正重试。 | PASS（安全停止） |
