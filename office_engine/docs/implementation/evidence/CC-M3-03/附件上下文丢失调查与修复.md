# CC-M3-03 附件上下文丢失调查与修复

日期：2026-11-16  
数据库：仅现有开发库 `odoo18e_llm`  
范围：M3 下游附件定位、Provider 上下文引用及新建 Odoo 导出路由

## 结论

发现并修复了 M3 的两个下游问题：

1. M2 的附件查找只扫描最近 25 条用户消息。上传后又有超过 25 条用户消息时，附件仍在当前 Thread 的 `message_ids` 关系中，但 `_office_latest_upload()` 找不到它，导致 Route B / Office 编辑流程看不到既有文件。
2. 对自然语言“整理成一个 Excel”的新建导出请求，M2 文件less意图词表没有“整理”等动词，M3 在生成前无法识别 Route B，因而没有给 Provider 绑定 Retriever / Office Tools 和 M3 导出指引。

本轮只在 `office_engine_m3` 下游覆写 Thread 行为。未修改 `odoo-llm` 或 M2 源码，未新增模型，不扩大 25 条 LLM 消息窗口。

## 实际线程与请求证据

### 线程 264：上传请求的实际原因

- 原始用户消息 `mail.message 461912`：要求将 WorldDepot 项目下全部出库订单及产品数量“整理成一个 Excel”，含订单号、Reference、日期；该消息没有附件。
- Provider 回复 `mail.message 461913` 要求上传项目导出文件或页面截图。
- ORM 读取的 Thread 264 当时 `tool_ids=[]`，且没有 assistant Tool Calls。使用相同消息检查 `_office_requests_fileless_workbook()` 和 `_office_is_active()` 均为 `False`。
- 该线程只有这一条用户消息，没有后续澄清。因此不能声称其澄清被遗漏；这一条原始需求已写入 Odoo 消息记录。
- 直接原因是意图词表不包含“整理”，不是附件内容被静默检索过滤，也不是 Office Schema 要求上传。

本地数据库未保留 OpenAI 原始 HTTP 请求体或完整 Provider 请求归档；可审计事实是消息、Thread 工具绑定状态与工具调用记录。由空 `tool_ids` 及实际 `prepare_chat_kwargs` 实现可确认该请求没有可用 Tools / M3 指引。未将推断写成原始请求体证据。

### 附件超过 25 条消息

此前 M2 `_office_upload_from_thread()` 对 `source_thread.message_ids` 过滤后按 ID 倒序，再切片 `[:25]`。因此它实际限制的是最近 25 条用户消息，而不是 LLM 上下文接口的 25 条消息。上传更早时，`get_llm_messages(limit=25)` 不包含上传消息，M2 附件扫描也无法找到它。

自动化回归在上传后追加 106 条无附件用户消息，确认上传消息已不在 LLM 最近 25 条历史内，但 M3 仍能从 Thread 关系找到文件；连续两次 Provider 参数构建都包含附件引用。该测试不声称真实 Provider 已在该压力场景运行。

## Schema、指令和权限核查

- M3 Office Schema 的 `export_records` 使用 `workbook_source=new/current`、`source_query`、`collections`、`tables` 和 `verification_profile`；不存在必需的上传附件参数。`workbook_source=new` 是新工作簿来源契约。
- M2 Route B 通用指令会让“无源空白 XLSX”使用 `action=create`。这与 M3 的 Odoo 数据导出使用 `action=export_records` 冲突；M3 现在在自己的 Provider 指引中明确区分二者，Odoo 数据新建导出无需空白文件或模板。
- 附件发现仍通过当前用户可读 Thread 的 `message_ids` 关系；`_office_engine_classify_attachments()` 及已有 Office 服务继续执行 `attachment.check("read")`。没有 `sudo()`、直接查询、文件字节拷贝或新附件处理路径。
- Office 工具读取附件仍调用现有 `thread._office_latest_upload()`；M3 的覆写因此同时用于 `edit_orchestrator` 和现有 M2 Session 处理。

## Silent Retrieval 核查

`llm_silent_retrieval` 仅用于 Discuss `_message_fetch`、SSE / Bus 用户可见消息过滤及失败恢复，不参与 `llm.thread.get_llm_messages()` 的上下文筛选。Provider 历史只排除非 LLM 消息及 `is_error=True` 消息，静默 assistant/tool 消息仍会进入后续上下文。新增测试实际断言两类静默消息仍在 `get_llm_messages()` 返回值中。

## 修复内容与自动化结果

- M3 覆写附件扫描，沿用 Thread 关系、当前用户作者筛选、附件签名分类和损坏 / 混合上传的 fail-closed 行为，移除 25 条附件历史扫描上限。
- 每次 `_prepare_chat_kwargs()` 生成仅文本的文件引用，包含文件名、消息 ID、附件 ID 和上传时间；不将文件二进制重复注入 Provider 上下文。服务端继续复用原有权限检查和 Office 附件读取流程。
- 用户当前消息明确包含历史附件文件名时，解析并优先选中该历史文件；上下文同时告知最新附件与被明确选择的历史附件。
- 为“整理 / 汇总 / 转成 / 做成 Excel”等中文表述增加 M3 通用 fileless 识别，并在导出指引中明确 `workbook_source=new` 不要求上传源文件。
- 修正 M3 Provider 指引中与 M2 空白工作簿 `action=create` 指令的冲突：空白工作簿仍走原有 `create`；Odoo 记录导出走 `export_records`。
