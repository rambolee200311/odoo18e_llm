## 3. 范围

### 3.1 范围内

1. 沿实际链路调查 Thread 866：Provider SDK response → Adapter / Odoo LLM 消息处理 → assistant `mail.message` 创建与事务提交 → Silent Retrieval 分类 → Bus/SSE → Discuss 历史读取 / UI。
2. 通过安全故障注入复现 handoff / 最终答复失败，精确定位消息在哪个可观察边界缺失；修复已证实的最小缺陷，公共 Provider / Tool 接口保持兼容。
3. 确保成功的纯 Retriever 内部 Tool Call / Execute 继续保持用户界面静默，同时保留内部消息、上下文、执行状态和诊断。
4. 确保最终成功答复、澄清、权限拒绝、查询 / handoff / Office 失败、Office 与 Retriever 混合消息、Candidate 及用户确认事件不会被误分类或整条隐藏。
5. 按操作副作用分类验证只读纠正、权限停止、明确失败后的状态检查以及写操作状态未知时的安全停止。
6. 运行受影响的自动化与组件集成回归；维护 IHR、ATR、必要的 RCA / Final Report。中间 CC 不做 UI HVR。

### 3.2 范围外

- 修改冻结 SRS、M4 TDD、Implementation Plan、M2/M3 冻结契约；改变 Provider、Tool、HTTP、Bus 或消息公共 API。
- 修复流式 generator 续接或声称完整流式路径已通过；流式路径只验证 TDD 要求的消息可见安全边界。
- 新增公开 Tool / 参数 / 错误码、持久化审计模型、独立恢复框架、治理或审批机制。
- 改写业务查询规划或重做 CC-M4-02；实现 Excel / 聚合功能或最终业务 UI E2E。
- 通过 `sudo()`、SQL、替代身份或放宽 ACL / Record Rules 恢复权限拒绝。
- 生产环境、数据库创建、部署、发布、人工 UI HVR。

## 5. 行为契约

### 5.1 最终消息生命周期

1. Provider 返回的最终答复、澄清或失败说明必须在 Odoo Thread 形成可持久读取的 assistant 消息。
2. 最终消息成功持久化并提交后，才可通过 Discuss、Bus 或 SSE 向用户发布。不得先广播后分类 / 持久化。
3. 刷新及重新打开 Thread 后，最终消息仍可读取；空答复或未持久化不得被呈现为成功完成。
4. 消息、请求、工具调用和状态间可用现有 ID 关联；缺失的 Provider request/response ID 标为不可得，不造 ID，不记录凭据。

### 5.2 Silent Retrieval 边界

| 消息类别 | 用户可见性 | 内部保留 |
|---|---|---|
| 成功的纯 Retriever assistant Tool Call 与 Execute | 按 M3 已验证路径不显示为冗余业务消息，且不提前经 Bus/SSE 暴露 | 保留 mail.message、原始参数/结果、Tool Call ID、LLM 上下文、执行状态与诊断 |
| Retriever 错误或权限拒绝 | 可见并准确说明未完成原因 | 保留原始错误码、诊断 ID 和执行回执 |
| Office 与 Retriever 混合调用 | 不因含 Retriever 而整条隐藏；Office 与必要文本保持现有交互 | 全部保留 |
| 最终业务答复、澄清、失败、Candidate/Accept/Reject/Finalize | 按现有 M2/M3 交互正常显示 | 全部保留 |

仅对已识别为纯 Retriever 且成功的消息执行静默规则；错误、混合工具、最终消息和用户确认不进入该过滤分支。

### 5.3 恢复与重试边界

| 操作 / 状态 | 允许行为 | 禁止行为 |
|---|---|---|
| Registry discover/describe 只读错误 | 依据实际错误调整检索表达或使用已返回候选继续 describe；单一阶段在原始调用外最多纠正重试 2 次 | 无限重试；把空候选说成模型绝不存在；猜测技术答案 |
| Retriever `INVALID_QUERY` / `FIELD_NOT_FOUND` | 只在保留全部用户业务条件且使用元数据 / 成功回执支持的修正后有限重查；单一阶段最多 2 次纠正重试 | 静默删减或放宽谓词、把错误报成零、超限继续请求 |
| Retriever 合法零结果 | 报告成功零结果；只有新证据或用户澄清后才改变查询 | 将零结果当作错误自动重试或推断全局无记录 |
| ACL / Record Rule 拒绝 | 准确报告当前用户不可读并停止；必要时请有权限的用户处理 | `sudo()`、换身份、改走其他路径绕权 |
| Office 写操作明确失败 | 先核对现有 Candidate / Current、附件、版本和 SHA，再按可证实状态作有依据的处理 | 只看异常文本就认定无副作用并盲目重复创建 / 覆盖 |
| Office 写操作状态未知 | 查询现有 call/session、Candidate / Current、附件、版本和 SHA；仍未知则停止并说明 | 状态查明前重发任何副作用操作 |

纠正重试次数是“原始调用之外、同一操作阶段最多 2 次”，所有尝试逐次留证，不以平均成功率掩盖失败。不能证明原条件、当前权限和副作用安全时停止。不得创建新 Candidate 作为错误恢复捷径；既有 M2/M3 Accept / Finalize 门禁不变。

## 8. 关闭标准

CC-M4-03 仅在负责人关闭评审前满足以下条件：

- Thread 866 的精确失败边界由实际证据确定；若仍 UNKNOWN，必须在 ATR 标为未通过或缺证据，不得声称已定位或修复。

- Silent Retrieval 保留内部记录且只隐藏成功纯 Retriever 消息；错误、混合工具和确认链不被隐藏。

- M2/M3 受影响回归通过；Provider / Tool 公共接口保持兼容；测试注入设施撤销且数据清理有证据。
- IHR、ATR、FR 完整；每个强制测试均有状态和证据；失败项按项目流程处置；最终由负责人决定关闭。
