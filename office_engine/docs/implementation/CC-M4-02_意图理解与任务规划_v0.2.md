## 1. 目标与背景

M4 TV 的 C02 / E05 表明：Agent 会遗漏用户明确提出的筛选条件，或者不能将多轮澄清与后续查询、输出要求连贯起来。RCA-003 同时确认，Thread 796 的查询参数漏掉了项目 Domain；另一个已确认问题是 `search(query=...)` 被 Schema 接受但执行路径未使用该参数。两类问题必须分别归因：Agent 没有表达正确计划属于规划缺口；工具收到参数后静默忽略属于接口契约缺口。

本 CC 的目标是：对信息充分、技术上可执行且当前用户有权访问的任务，Agent 必须完成用户明确要求，并使最终业务结果与独立 Oracle 一致。约束按完整执行链追溯到模型/字段/关系选择、Retriever 查询、关联数据获取、结果处理及输出验证；不要求所有条件出现在单次 Domain。Retriever 对当前 operation 明确不适用的已知参数必须清楚拒绝，旧调用保持兼容。

只有存在真实业务歧义、权限限制或可复核的技术障碍时，才允许 Agent 澄清或准确报告未完成；不得以主动放弃可执行任务代替正确规划。Tool Call 成功、参数 JSON 合法或 Agent 自述“已考虑”均不单独构成 PASS。

## 3. 范围冻结

### 3.1 范围内

1. 在 Agent 当前任务上下文中继承用户原始目标、明确约束和相关澄清结果，并能用用户消息、可观察工具调用/结果及测试 Oracle 建立约束追溯矩阵。
2. 冲突时优先遵循当前用户最新的明确指令；用户只修改部分条件时，其他未修改且仍有效的条件继续生效。旧任务要求、Agent 既有计划或工具输出不得覆盖与之冲突的当前用户指令。
3. 允许 Agent 根据 Registry 元数据、`describe` 和合法的只读查询结果动态修订后续计划；不要求最初即掌握所有模型、字段或调用顺序。
4. 验证多条件自然语言要求是否完整落实到正确模型、字段、关联范围、Domain、排序/全量语义及输出检查目标；不把隐藏 Chain-of-Thought 作为证据。
5. 在现有 `odoo_record_retriever` operation 分发中，拒绝与 operation 不适用的已知参数；`search` 收到 `query` 时返回现有 `INVALID_QUERY`，不得静默忽略。
6. 保持省略 `operation` 的旧版 search 调用和当前响应兼容，并验证实际 Provider Tool Schema、Tool Execute 与 ORM 行为一致。
7. 用当前用户可见数据区分合法零结果、非法查询、字段/模型错误及权限拒绝；不扩大权限，也不将失败折叠为零结果。

### 3.2 范围外

- CC-M4-01 的 Registry 候选召回算法和 Agent 选模准确率改造；仅把其已关闭能力作为输入依赖。
- CC-M4-03 的最终消息持久化/Bus/SSE 修复、操作失败恢复次数和跨消息恢复策略。CC-M4-02 不冻结重试次数。
- CC-M4-04 的公式、聚合、Excel 输出验证实现。
- CC-M4-05 的完整真实 UI E2E、真实用户 Accept / Finalize 和业务 HVR。
- M3 Collector、分页/关联收集、handoff 及文件生成行为的重新设计；仅在验证约束到结果的追溯时调用已有能力。
- M5 式历史上下文分级、跨任务记忆或独立计划存储；不新增数据库模型、字段、缓存或长期记忆机制。
- 新增公开 Tool、公开参数、Provider 公共接口或业务专用规划器；不硬编码模型、字段、项目、业务词、Domain、模板或测试答案。
- 更换用户身份、`sudo()`、SQL / RPC 绕过、放宽 ACL / Record Rules；不修改冻结 TDD、Implementation Plan 或 CC-M4-01。

## 5. 必需行为与接口契约

### 5.1 当前任务约束继承

- 测试以用户自然语言作为唯一业务意图来源；Agent 不得收到 Oracle 中的模型名、技术字段名、Domain 或正确 ID 集。
- 对每个可观察的用户要求，记录其当前状态：有效、由用户明确修改、由用户撤销、需澄清，或因技术限制未完成。测试证据不要求增加产品状态模型。
- 新的用户明确指令与先前条件冲突时，以最新指令为准；没有被修改的条件继续有效。单纯的工具结果或 Agent 旧计划不构成用户修改。
- 字段、关系路径及状态值必须有 `describe`、现有 Registry 元数据或合法只读查询结果作为依据；Agent 不得把未经验证的字段名、状态值或关系路径直接用于查询并据此宣称成功。
- 以完整执行链追溯每项约束。条件可以由多个合法的只读查询、跨模型关联数据获取、结果处理和输出验证共同满足；不要求所有约束都编码在首次或单次 Domain 中。
- 使用独立 Oracle 验证完整约束覆盖、最终可见结果集合及用户要求的输出内容；Tool Call 参数只是证据之一，不单独决定 PASS。不得要求或采集隐藏推理文本。
- 若信息足以只读发现技术对象，Agent 可先 `discover / describe / search` 再调整计划。只有业务含义仍不唯一且不同解释会改变结果时，才要求用户澄清。
- 在无实际歧义、权限限制或技术障碍且任务可执行的场景中，Agent 必须继续规划并完成任务；主动放弃、遗漏条件或仅报告“未完成”均为 FAIL。

### 5.2 Retriever operation 参数拒绝

| 调用 | 期望行为 |
|---|---|
| `operation="discover"` 且 `query` 合法 | 按现有发现契约执行，响应兼容 |
| `operation="describe"` 且参数合法 | 按现有描述契约执行，响应兼容 |
| `operation="search"` 且 `domain` 合法 | 按当前用户 ORM 权限执行 |
| `operation="search"` 且包含不适用的 `query` | 明确返回现有 `INVALID_QUERY`；不得忽略参数后执行宽泛搜索，也不得伪装成成功零结果 |
| operation 缺省的 legacy search 调用 | 保持 CC-M3-01 已验证的兼容行为、调用形状及响应 |
| 其他 operation / 参数组合 | 按当前已存在的工具契约验证；除冻结 TDD 明确要求外，不发明新错误码或公开响应字段 |

Provider Schema、Tool Execute 和 ORM 是三层不同边界：必须用实际请求/调用证据确认非法参数不会被 Schema 接受后静默丢弃。若 Provider Schema 不能表达拒绝条件，由执行层保持 fail-closed 并返回现有 `INVALID_QUERY`；不得为通过测试而改动公开工具名称或无关接口。

参数兼容边界：只拒绝与当前 operation 明确冲突且会改变调用含义的已知参数；本 CC 不引入全局严格参数白名单，不借此拒绝既有合法调用或重构无关参数契约。

### 5.3 结果与错误语义

- 合法 Domain 返回零条可见记录时，保持成功零结果语义。
- 非法/不适用参数返回 `INVALID_QUERY`；字段/模型错误、权限拒绝和运行查询失败按现有错误码区分。
- Record Rules 下的 count 只代表当前用户可见集合，不推断全局数据总数。
- Agent 若未能落实明确约束，或工具返回错误，不能把该任务报告为已完成。

每条样例分层记录“Agent 计划遗漏”“operation 参数契约拒绝”“Provider Schema 表达”“Tool Execute 检查”“ORM 执行”及“Oracle 结果”状态，避免把一层缺陷归到另一层。Agent 未到达的后续环节标 `NOT REACHED`，不得据此宣称下游已失败或通过。

## 9. 测试环境与授权边界

- 数据库仅为现有开发库 `odoo18e_llm`；使用 Odoo ORM 建立与清理隔离的合成业务测试记录，覆盖真实关系并由普通测试用户执行实际 Retriever 查询。禁止创建其他数据库、访问生产环境、执行直接 SQL 或修改现有真实业务记录。

- 真实 Provider、模型和工具绑定必须在后续冻结 CC / 执行授权内明确；本 Draft 不构成外发授权。
- 测试只写入本 CC 创建的合成业务记录、Thread 与 fixture；不修改真实业务记录。清理须用 Odoo ORM 复核，并保留必要 Provider 调用审计。
