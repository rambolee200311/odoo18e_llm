## 1. 目标与结果

在现有唯一公开工具 odoo_record_retriever 中，提升通用 discover 候选发现，使 Agent 能从中文、英文、短语、长句、单复数和同义表达中找到正确的 Registry 模型；对会改变业务范围的歧义，不擅自选择而应继续只读发现或向用户澄清。

验收重点是完整 Registry 上的候选召回、排序、歧义处理、错误候选、性能，以及 Agent 对候选的实际选择。固定候选小样本或 Provider 单次排序结果不能代替完整 Registry 及 Agent 集成证据。

## 3. 范围冻结

### 3.1 范围内

1. 在现有 odoo_record_retriever 的 discover 操作内实现通用候选召回及稳定相关性排序；采用 TDD 冻结方向：通用语义候选发现为主，可配置业务别名为可选补充。
2. 在运行时完整 Registry 上验证候选生成、分页、排序、空结果和歧义处理；测试不依赖固定的模型子集作为候选全集。
3. 验证 Agent 可通过现有 discover / describe 工具结果选择正确模型；工具结果可以包含 Registry 技术名和描述，测试程序不得把隐藏 Oracle 中的答案预置给 Agent。
4. 若通用 Agent 指令确有必要，只允许在 TDD §5.1 范围内调整 discover / describe 的使用与歧义处理指导；不得引入模型专用提示或替代用户业务规划。
5. 如评估可配置别名补充，比较其对召回、误候选、歧义及维护成本的影响；可得出“不采用别名”的结论。不得让别名成为唯一发现路径或权限边界。
6. 建立盲测集、独立 Oracle、自动化和组件集成测试，保留 IHR / ATR 所需的可复核原始证据。

### 3.2 范围外

- 新增公开 Registry / Discovery Tool、operation、业务对象查询 Tool 或修改现有 Provider 公共接口。
- 修改现有 discover / describe / search 的权限语义、成功响应主要结构或 legacy search 兼容行为；不新增公开 score、confidence、策略或映射审批字段。
- 自然语言业务条件抽取、完整查询规划、Domain 生成、关联结果完整性交付；属于 CC-M4-02 及 M3 已冻结能力。
- Office 路由、Collector / handoff、Excel 生成、公式/聚合、Candidate 生命周期、消息持久化与失败恢复；属于其他 CC。
- 新建业务模型、审批/治理流程、独立审计系统、额外业务权限、sudo()、SQL/直连数据库、特定模型或业务词硬编码。
- 修改上游 odoo-llm 公共 API、M2/M3 冻结行为、TDD、Implementation Plan、原始 TV/RCA 结论。
- UI HVR、人工 Accept/Finalize、生产环境访问、创建数据库、部署或发布。

### 3.3 非目标

- 证明 Office Agent 已达到 STD-01～03 全部标准。
- 将 SPK 中一次 Provider 排序原型直接并入产品。
- 为一次性盲测表达编写词条、别名或特殊匹配规则。
- 以固定 Registry 子集、测试样例通过或工具调用成功替代完整 Registry 验收。

## 11. 测试契约

以下样本量与量化验收值按本次冻结决定执行。Retriever 候选召回与 Agent 最终选模分别判定、分别归因；最终报告不得以总体平均数掩盖任何语言、模型或歧义类别的失败。

### 11.1 盲测集与判定前置

- 从实际 Registry 独立抽取不少于 10 个不同模型作为目标模型；对候选检索运行完整 Registry，不把这 10 个模型组成的固定子集伪装为完整候选池。
- 至少 40 条明确业务对象意图（每目标模型至少 4 种不同表达）及 8 条歧义表达：其中至少 4 条可由只读 discover / describe 消解技术歧义，至少 4 条在只读发现后仍有会改变结果的业务歧义；另设至少 6 条无匹配/无法判定的负向表达。
- 明确表达须平衡覆盖中文/英文、短语/长句、同义表达、单复数及未见过的表面说法。测试句不得直接复制 Registry 技术名或技术描述形成答案提示。
- 盲测按表达分层；标签在独立 Oracle 文件中保存并在生成测试表达/候选集后封存。保留盲测集及 Oracle 的版本/哈希和可访问边界。
- 对完整 Registry 记录模型总数、返回候选数、候选顺序、分页参数及各阶段耗时；不将逐页请求中的局部排序当作全局排序。
- 至少抽取 6 条表达在 3 个独立 Thread 中重复验证，分别覆盖明确意图和实质歧义；逐次结果单独判定，不以平均值替代。
- 每条 Agent 样本分别记录 Retriever Top-5 召回状态/目标排名、Agent 选模状态（PASS / FAIL / NOT REACHED）、最终业务对象发现结果及失败归因。失败归因至少区分 Retriever 目标未召回、目标已召回但 Agent 选错、明确意图下不必要澄清、未澄清实质业务歧义、工具未传递/未调用和 Provider/执行错误。

## 12. 停止条件 / 升级闸门

1. 必须改变 TDD 技术方向、公共 Schema / 响应、引入新公开 Tool、持久化核心模型或新依赖：停止并提交 TDD 变更评审。
2. 需要读取业务记录、使用 sudo/SQL/替代身份或改变 ACL / Record Rules 才能发现模型：停止并提交权限设计评审；不得实施绕过。
3. 盲测标签或目标模型答案进入 Agent 上下文、测试提示或 Provider 请求：该轮证据作废，修复隔离后重新执行，不得用其判 PASS。
4. 内部候选评分只用于相关性排序，不作为公开置信度或业务权限；评分阈值与候选池参数作为实现级局部决策记录在 IHR，并必须满足冻结的独立 Top-5 召回和 Agent 选模门槛。目标未进入 Top-5 时，该案例 Agent 选模状态记为 NOT REACHED，归因为 Retriever 召回失败；整体业务对象发现案例仍为失败。目标已进入候选但 Agent 选错时，单独归因为 Agent 选模失败。若采用 Alias，重复命中去重、冲突候选保留并继续相关性排序，不得用 Alias 强制覆盖语义候选或歧义澄清。
5. 开发库/Provider/Thread 工具配置无法确认，或环境指向生产/新建数据库：停止相关测试，报告原始状态；不得切换到其他数据库。
6. 任何 Office 写操作、业务记录写入、文件 Candidate 或 M2 生命周期操作被纳入：超出范围，停止并交由相应 CC 处理。
7. CC 范围或验收阈值需在实施期间扩大、削弱或改变：先修订 CC 并重新获批，不得静默调整。

## 13. 完成定义 / 关闭标准

CC-M4-01 仅在以下条件全部满足后提交关闭评审：

- 完整 Registry 盲测集、Oracle 隔离、指标和性能记录均符合本 CC 冻结版本。
- 自动化候选召回、排序、分页、歧义、空结果、权限边界及 legacy 兼容验收全部有逐项状态和证据。
- 已授权的 OpenAI GPT-5.6 Luna 组件集成记录了工具配置、请求 Schema、Provider Tool Call、Odoo Execute、Agent 最终选模/澄清；无 UI HVR。
- 所有适用测试状态明确；失败/阻断/未执行证据原样保留，不得按平均分或原型结果覆盖。
- M3/M2 定向回归无本 CC 引入的回归；未执行的全量回归不宣称通过。
- IHR、ATR 和 Final Report 准备齐全；代码/文件差异限于本 CC；关闭评审获负责人批准。

本节为计划门禁，不填写实际执行状态。最终实施证据由 IHR / ATR / Final Report 提供。
